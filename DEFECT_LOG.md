# DEFECT_LOG — SpendWise

This log records **real defects and incidents actually encountered** during
development of SpendWise, each verified against the codebase at the time it
happened. No speculative or planned-but-unobserved issues are listed.

| # | Phase | Defect / incident | Steps to reproduce | Impact | Root cause | Resolution | Fixed? |
| --- | --- | --- | --- | --- | --- | --- | --- |
| D-01 | Batch source edits | A PowerShell-based bulk text update (`Get-Content` / `Set-Content` without an explicit encoding) risked corrupting UTF-8 file contents | Run any `Get-Content x \| Set-Content x` rewrite on a UTF-8 Dart file under Windows PowerShell 5.1, then re-read the file — non-ASCII bytes are re-encoded | Potential source corruption across edited Dart files | Windows PowerShell 5.1 defaults to legacy encodings | Verified every `lib/` and `test/` file byte-by-byte as UTF-8 and switched to UTF-8-safe tools (Python `pathlib` with explicit `encoding='utf-8'`, plus editor-based edits) | **Yes — verified** |
| D-02 | Deprecation cleanup | A bulk Python regex replacing `withOpacity(x)` with `withValues(alpha: x)` over-matched nested call sites and inserted stray `)` characters | Run the unbounded regex over `lib/` (e.g. `Color(a ? x : y.withOpacity(z))` ternaries), then run `flutter analyze` — ~250 paren-balance errors appear | ~250 analyzer errors after the rewrite | Regex `[^(]`-sanity pass was insufficient for nested `Color XOR (...)` ternaries | All affected files restored from the previous Git commit (`c528be1`), the replacement re-run with a corrected safe pattern (`withOpacity\(([^()]+)\)`), and all remaining files individually verified. Post-incident rule adopted: no bulk regex refactors of code without a per-file diff check | **Yes — restored + rewritten** |
| D-03 | Analyzer sweep | `flutter analyze` initially reported 250 issues (stray parentheses corruption above, unused imports, misplaced `library;` directive, a `[..list]` typo where a spread `...list` was intended, deprecated `opacity` getters/`withOpacity` calls) | Run `flutter analyze` immediately after the D-02 rewrite | Build blocker | Combination of D-02 and normal drift | Fixed file by file; final scan (`flutter analyze`) reports **No issues found** | **Yes — verified** (`flutter analyze` exit 0) |
| D-04 | Analyzer sweep | `lib/widgets/spending_chart.dart` still contained a deprecated `Color.opacity` ternary after the global rewrite | Run `flutter analyze` after the D-02 fix pass — one deprecated-member warning remains in the chart widget | Analyzer warning | Ternary not covered by the safe regex pattern | Manually replaced with `barColor.withValues(alpha: 0.85)` | **Yes — verified** |
| D-05 | Analytics correctness (test defect) | The provider test "monthly and today spending reflect the current month" used `yesterday = today - 1 day` for the "previous month" record. On the 1st–2nd of a month the test expectation itself becomes wrong (e.g. on 03 Nov 2026 the record falls inside the current month, so `monthlyExpense` = 390 not 140) | Run `flutter test` on the 1st or 2nd day of any month with the old fixture — the monthly-summary assertion fails | Wrong test data — not an app bug; the app's calendar-month slicing (`monthKey(date) == monthKey(now)`) was verified correct | Test fixture was date-dependent | Fixture changed to canonical previous-month dates (`DateTime(now.year, now.month - 1, 1)`), assertions unchanged (still expects 140). Suite is now identical on any calendar day | **Yes — verified** |
| D-06 | Widget tests | `InMemoryStore` accepted a `seed` list in its constructor but never loaded it into the live record map; seeded dashboard tests saw zero records (`₹0`, `0 records`) | Run `flutter test test/dashboard_screen_test.dart` with the seeded fake — dashboard renders the empty state instead of the seed records | 5+ widget tests failed / gave false coverage | Constructor never invoked `reset()` | Fake now loads seed data in the constructor; all dashboard tests observe the seeded records | **Yes — verified** |
| D-07 | Widget tests | Dashboard tests asserted on widgets below the default 800×600 test surface (`CustomScrollView` performs lazy building; the Save button of the tall form is beyond build extent) | Run the form-flow widget tests at the default 800×600 surface — "Save button not found" failures | False-failing tests, not an app defect | Test viewport smaller than the scrollable content | Test harness now uses a tall logical surface (800×1400) with `addTearDown` reset; no product code was weakened and lazy rendering is preserved | **Yes — verified** |
| D-08 | Widget tests | "Non-numeric amount" test typed `12x3`, but the input formatter strips letters, so the field became valid `123` and the intended error could never appear | Enter `12x3` into the amount field — letters are stripped live, leaving `123`, so the numeric-error branch never triggers | Test asserted on an unreachable state | Paste simulation fought the real input formatters | Test now simulates the junk that *can* survive sanitising (malformed decimal `1.2.3`); the app's `Amount must be numeric` path is genuinely exercised | **Yes — verified** |
| D-09 | Form UX defect | Submitting with an empty payment method rendered the same error message **twice**: once from `_LabeledSection` and again from the `DropdownButtonFormField` validator | Open Add Expense → leave Payment method unset → tap Save — two identical error rows appear under the field | Duplicated error row; noisy UI | Equivalent validation wired at two levels in `add_expense_screen.dart` | Removed the redundant dropdown validator; the section-level message remains the single source | **Yes — verified** |
| D-10 | Widget tests | Add/Edit flow tests pumped the screen as `MaterialApp(home: …)`; the success-path `Navigator.pop` popped the only route, leaving no Scaffold to host the success SnackBar | Run the save-success widget test with the form as the only route — SnackBar assertion fails after pop | Impossible to assert success messages | Test topology differed from real usage (details screen shows beneath) | Tests now push the form above a host page, as the real app does; snackbars and the pop are both verified | **Yes — verified** |
| D-11 | Launcher icon | `flutter_launcher_icons` was configured with `android: "launcher_icon"`, but the manifest references `@mipmap/ic_launcher` — the custom icon would not have been picked up | Build the APK, install it, check the launcher — the default Flutter icon appears instead of the SpendWise icon | Launcher icon regression risk | Config/manifest name mismatch | Regenerated using the default name (`android: true`) so the generated `ic_launcher.xml` + mipmaps match the manifest reference | **Yes — verified** |
| D-12 | Android resources | The `android/app/src/main/res` directory was accidentally deleted (`Remove-Item -Recurse`) during workspace cleanup | Attempt `flutter build apk` with `android/app/src/main/res` missing — resource/link errors (splash theme, mipmaps, colours unresolved) | Splash theme, night styles, colours and all launcher mipmaps missing | Operator error (unsafe command) | Reconstructed from the standard Flutter template (`drawable/launch_background.xml`, `drawable-v21/`, `values/styles.xml`, `values-night/styles.xml`) and regenerated all generated resources (adaptive icon XML, colours.xml, all-densities mipmaps) via `flutter_launcher_icons`; full tree verified on disk and by release build | **Yes — verified/rebuilt** |
| D-13 | Analyzer sweep | Remaining final analyzer issues after the restore: unused detail-screen import in the navigation shell, `SingleChildWidget` type reference after cleanup, spread typo `[.._expenses, …]`, misplaced `library;` directive | Run `flutter analyze` after the D-12 restore — 4 residual errors are reported | 4 analyzer errors | Drift from interrupted restore sequence in D-02 | Fixed individually; final `flutter analyze`: **No issues found** | **Yes — verified** |
| D-14 | Release build | Every `flutter build apk --release` attempt failed mid-build with unrelated errors each time: `Unable to delete directory …/build/...`, Kotlin "could not close incremental caches / different roots", `AccessDeniedException` on `merged_native_libs` (each run after a JVM/daemon crash left stale locks) | Run `flutter build apk --release` on a machine where the pub cache/Gradle home are on `D:` while the project is under OneDrive on `C:` — the build dies at a random mid-build step with delete/access errors | Repeated blocked builds spanning several restarts | (a) Kotlin incremental caches cannot relativize paths across drive roots (pub cache on `D:`, project on `C:`), and (b) OneDrive file-sync locks files inside the workspace `build/` directory on Windows | `kotlin.incremental=false` in `android/gradle.properties` (with explanatory comment) + killed orphan Gradle daemons and paused OneDrive locally, purged the `build/` tree before the final build, then re-enabled OneDrive | **Yes — release APK built successfully (53,355,349 bytes)** |
| D-15 | Android config | `applicationId` was `com.spendwise.spendwise` (Flutter's default `--org` + project-name concatenation), while the approved configuration requires `com.spendwise` | Inspect `android/app/build.gradle.kts` → `applicationId`; or `aapt dump badging app-release.apk \| grep package` on the earlier build | App identity did not match the submission requirement | Template default | Set `applicationId = "com.spendwise"` in `android/app/build.gradle.kts`; the Kotlin `namespace`/package structure was left intact so `MainActivity` keeps resolving; final APK rebuild verified | **Yes — verified/rebuilt** |
| D-16 | Web delivery | CSV export on web threw a platform error: the export used `path_provider`/`dart:io` file APIs that do not exist in a browser | Open the web build → Settings → Export to CSV with at least one transaction — the failure snackbar appears instead of a download | Feature broken on the web deliverable | Android-only file sink used unconditionally | Platform-routed export via conditional imports (`export_target_io.dart` writes to app documents; `export_target_web.dart` triggers a browser download via `package:web`); Android behaviour unchanged | **Yes — verified** (analyze clean, 33/33 tests, web rebuilt) |
| D-17 | Web delivery | Web preview originally used an in-memory store: all records vanished on page refresh | Open the early web build, add a transaction, press F5 — the record is gone | Data-loss appearance on the web deliverable | Browsers cannot load the mobile `sqflite` plugin; a temporary in-memory fallback was used | Replaced with real SQLite-WASM persistence (`sqflite_common_ffi_web`, OPFS/IndexedDB) + COOP/COEP headers on the server and `web/vercel.json`; the in-memory fallback was deleted | **Yes — verified** (persistence survives reload on the live site) |
| D-18 | Dashboard UI (stale greeting) | The dashboard header kept showing "Good Morning" after midday when the app had been opened in the morning and resumed from background | Open the app in the morning → leave it in background (home button) → reopen after 12:00 — the header still shows the morning greeting even though the current time is afternoon | Time-dependent header (greeting + date) froze at first build | The greeting is computed from `DateTime.now()` at build time, and the body was a `const` widget, so Flutter skipped rebuilding it when the lifecycle wrapper rebuilt | Added a `WidgetsBindingObserver` to the dashboard lifecycle wrapper: on `AppLifecycleState.resumed` it calls `setState`, and the body child is no longer `const`, so the header recomputes on every resume | **Yes — verified** (analyze clean, 33/33 tests pass) |
| D-19 | Search field (reversed text) | Typing in the dashboard search box produced reversed text on Android (e.g. typing "hiiii" rendered "iiiih") | Focus the dashboard search field on a physical phone with Gboard → type any word — characters appear in reverse order | Search unusable on Android; text scrambled | `_SearchField` created a **new `TextEditingController` inside `build`** seeded from the provider; every keystroke rebuilt the widget, the fresh controller reset the IME composition session and caret, and the keyboard re-inserted text at position 0 | Converted `_SearchField` to a `StatefulWidget` owning a single controller for its lifetime; the provider still receives updates via `onChanged` and the clear button resets the same controller | **Yes — verified** (analyze clean, 33/33 tests pass) |
| D-20 | CSV export unreachable on Android | The exported CSV was written to the app-private documents directory (`/data/user/0/com.spendwise/...`), which no file manager can browse — users could not find the file and concluded export "does not save" | Export to CSV on Android → the dialog shows a `/data/user/0/...` path → open any Files app and try to navigate there — impossible without root | Exported data effectively inaccessible to the user | `getApplicationDocumentsDirectory()` returns app-internal storage on Android | The IO export now opens the **system share sheet** (`share_plus`) after writing the file, letting the user save it to Files, Drive, WhatsApp or any target; the internal copy path is still shown for reference | **Yes — verified** (analyze clean, 33/33 tests pass) |
| D-21 | Chart labels (collision) | In the dashboard's last-7-days chart the "Yesterday" label was wider than its bar slot and collided with the "Today" label, wrapping to two lines | Open the dashboard on a narrow phone → look at the last two bars of the Spending Overview — "Yesterd/ay" overlaps "Today" | Chart x-axis unreadable at the week's end | "Yesterday" exceeded the per-bar label width; the painter wrapped it instead of clipping | Abbreviated the label to "Yest" in `DateFormatter.dayLabel`; all seven labels now fit their slots with visible gaps | **Yes — verified** (analyze clean, 33/33 tests pass) |
| D-22 | Summary amount truncation | Large all-time totals (e.g. ₹1,13,602) were ellipsised to "₹1,13…" in the Income/Expenses summary tiles | Enter enough transactions that the all-time total exceeds ~6 digits → the Expenses tile shows a truncated amount | Fixed-size `Text` with `TextOverflow.ellipsis` inside the tile | The amount text is now wrapped in `FittedBox(fit: BoxFit.scaleDown)`, so long values shrink to fit instead of being cut | **Yes — verified** (analyze clean, 33/33 tests pass) |
